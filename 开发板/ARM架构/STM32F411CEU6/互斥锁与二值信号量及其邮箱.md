## 2. 逐点精讲

### 知识点 1：信号量的概念及其使用

#### 实际意义

信号主要用于任务和任务以及中断之间的同步和事件通知

#### 通俗人话解释

信号量可以理解为手机电话铃声，铃声一响就知道有电话打来

#### 关键公式/结论

1. 二进制信号量，用于互斥和同步，但是二进制信号量不会优先级继承，相比于互斥，更适用于同步，只有 0 和 1 两种状态
2. 计数信号量，多用于盘点事件如事件 a 被触发了多少次，同时用于管理系统可用资源，任务每获得信号量一次就代表使用了系统资源，信号量为 0 则没有空闲资源可用
3. 互斥量，是具有优先级继承的二进制信号量，更适用于任务之间任务与中断之间的互斥，用来保护系统资源，优先级继承机制就像是传承玉玺，谁拿到手里谁为皇帝，这时其他人的地位要低于皇帝，==注意在中断中不能使用互斥量==，其原因为互斥锁使用的优先级继承机制要求从任务中（而不是从中断中）拿、走和放入互斥锁；中断无法保持阻塞来等待一个被互斥锁保护的资源变为可用。

#### 递归互斥量（Recursive Mutex）

##### 概念

递归互斥量是互斥量的一种变体，==允许同一个任务重复获取（嵌套获取）同一个互斥量而不会把自己锁死==。每次成功获取内部计数 +1，必须释放相同次数后，互斥量才对其他任务真正可用。在 FreeRTOS 中通过 `xSemaphoreCreateRecursiveMutex()` 创建，需在 `FreeRTOSConfig.h` 中使能 `configUSE_RECURSIVE_MUTEXES`。

##### 实际意义

普通互斥量存在一个隐蔽陷阱：==如果持有互斥量的任务再次去获取同一个互斥量，会直接死锁（自己锁死自己）==。递归互斥量消除了这个限制，让 " 锁内再调锁 " 成为可能，避免为了规避重入而被迫拆函数、删锁或写重复代码。

##### 通俗人话解释

普通互斥量像一把 " 一次只能进一个人的房门 "——门里的人想再开门，反而把自己锁在屋里；递归互斥量像一张 " 可重入的电梯卡 "——刷卡进电梯后，在电梯里再刷几次卡电梯照常运行，但**刷了几次卡就必须出几次门**：刷 3 次卡，必须刷回 3 次，电梯才真正空出来给别人用。

##### 核心逻辑/原理（FreeRTOS 内部机制）

递归互斥量本质是 " 带持有者计数 " 的互斥量，创建时队列类型为 `queueQUEUE_TYPE_RECURSIVE_MUTEX`，内部用 `uxRecursiveCallCount` 记录嵌套次数：

```c
/* xQueueTakeMutexRecursive 简化逻辑：获取 */
if (pxCurrentTCB == pxQueue->pxMutexHolder) {
    /* 自己已持有 → 直接计数 +1，不阻塞、不死锁 */
    pxQueue->uxRecursiveCallCount++;
    return pdPASS;
}
xQueueGenericReceive(...);             /* 首次/他人持有时才真正排队 */
pxQueue->uxRecursiveCallCount = 1;
pxQueue->pxMutexHolder = pxCurrentTCB;

/* xQueueGiveMutexRecursive 简化逻辑：释放 */
if (pxCurrentTCB != pxQueue->pxMutexHolder) {
    return pdFAIL;                     /* 非持有者不能释放 */
}
if (--pxQueue->uxRecursiveCallCount == 0) {
    xQueueGenericSend(...);            /* 计数归零才真正释放给其他任务 */
}
```

##### 关键公式/结论

| 维度 | 普通互斥量 | 递归互斥量 | 二值信号量 |
|------|-----------|-----------|-----------|
| 同任务重复获取 | ==死锁== | 允许（计数叠加） | 死锁 |
| 释放条件 | take 1 次 → give 1 次 | take N 次 → give N 次 | take 1 次 → give 1 次 |
| 优先级继承 | 有 | ==有（FreeRTOS）== | 无 |
| 中断中使用 | 禁止 | 禁止 | 允许 FromISR |
| 典型用途 | 保护共享资源 | 递归 / 嵌套加锁 | 任务间同步 |

1. 必须使用专用 API `xSemaphoreTakeRecursive()` / `xSemaphoreGiveRecursive()`，**不能**混用普通 `xSemaphoreTake()/xSemaphoreGive()`
2. ==只有持有者能释放==，非持有者调用 give 返回 `pdFAIL`
3. 嵌套深度受 `uxRecursiveCallCount` 变量类型上限约束（至少支持 127 层，远超实际应用需求）

##### 常用应用场景

1. **递归函数访问共享资源** — 递归遍历树/链表时，每一层递归都要访问同一块受保护内存（如内存池、打印缓冲），递归锁避免中间层把自己锁死
2. **分层 API 嵌套调用** — 库函数 A 内部加锁，A 又调用同样加锁的内部函数 B；用普通互斥量会在 A→B 时立刻死锁，递归锁让层次化封装成为可能
3. **" 整包保护 + 元素保护 " 双层锁** — 外层锁保护整条消息收发，内层锁保护单个字符/字节输出（FreeRTOS 官方示例场景）
4. **状态机 / 协议栈重入** — 同一任务在不同状态下都要进入同一临界资源，调用路径上可能重复加锁

##### 常见误区

| 误区 | 真相 |
|------|------|
| 递归锁能解决所有死锁 | 只能解决 " 同任务重入 "；两个任务互相持锁等待（ABBA 死锁）它救不了 |
| take 几次只 give 一次就行 | ==必须严格配对==，少 give 一次互斥量就永久锁住其他任务 |
| 拿递归锁当信号量做同步 | 它是互斥/保护资源用的；任务间 " 发信号 " 请用二值/计数信号量 |
| 有了递归锁就不怕锁内耗时 | 递归锁会让持有时间变长（多层嵌套），高优先级任务可能被阻塞更久，能重构就别嵌套 |
| 中断里也能用递归锁 | ==禁止==，与普通互斥量一样不能从中断获取/释放 |

### 知识点 2：邮箱的概念及其作用

#### 实际意义

邮箱是用于任务之间的同步与通知，以任务通知为基础

#### 通俗人话解释

邮箱不止是通知别人有信件，它同时携带着信件，而且是有指定人的，其他人不能接收到

#### 关键公式/结论

1. 邮箱相比于队列、[[信号量]]，通知任务解除阻塞状态的速度要快 45%，消耗的 RAM 也更小
2. 同时也可以作为信号量、队列、事件组使用，不过只能 1 发送 32 位值，1. 该值保存为接收任务的 [通知值](https://freertos.org/Documentation/02-Kernel/02-Kernel-features/03-Direct-to-task-notifications/01-Task-notifications)，然后 在任何时间只能有一个通知值

### 知识点 3：环形缓冲区

#### 实际意义

用于缓存数据流，当大小不确定的缓冲区即可使用环形缓冲区

#### 应用场景

#### 常见误区

因为缓冲区成头尾相连的环形，写操作可能会覆盖未及时读取的数据，有的场景允许这种情况发生，有的场景又严格限制这种情况发生。选择何种策略和具体应用场景相关。

## 4. Q&A

### Q 1：互斥锁和二值信号量有什么区别？

 A 1:

 1. 互斥锁是一种有优先级继承机制的二值信号量，多用于互斥
 2. 二值信号量没有优先级继承机制，多用于同步

### Q 2：是否可以用二值信号量来做线程 A 和线程 B 之间的 buffer 访问的同步？

A 2: 不能，使用互斥锁的优势是优先级继承机制，这会让线程 AB 在获得互斥锁后不会被其他高优先级线程打断，导致丢数据，同时也能加快数据处理速度

### Q 3：如何线程 A 在获取互斥锁之前，不 queue_peek 去检查线程 B 的邮箱接收队列是否被邮箱取走，会发生什么情况

A 3: [[线程]] B 的接收队列数据还没有清空，而线程 A 发送数据给队列将旧数据覆盖，导致丢数据

### Q 4：如果线程 B 不先使用 queue_peek 去检查邮箱接收队列，直接使用 queue_receive 接收，然后去取互斥锁，将可能出现什么漏掉数据的情况？

A 4: 如果线程 B 不先使用 queue_peek 去检查邮箱接收队列，而是直接使用 queue_receive 去接收的话，可能线程 B 刚拿队列的数据，还没拿锁就被切换出去，此时线程 A 检查队列发现为空，拿锁发现可以成功获得就会误以为线程 B 已经将数据处理完毕，此时就会去启动 DMA 转换，回到线程 B 之后，很可能 buffer 的数据已经被新的 DMA 数据覆盖了，导致数据遗漏。

### Q 5：是否可以想出一种不使用互斥锁也能实现同步和数据不冲突的方案？同时也能应用到共享 Memory 来实现零拷贝？

A 5:

1. 使用无锁环形缓冲区
2. 内存池（未使用过）

### Q 6：递归互斥量和普通互斥量有什么区别？什么场景下必须用递归互斥量？

 A 6:

1. 区别：普通互斥量被同一任务二次获取会死锁；递归互斥量允许同一任务嵌套获取，内部用计数（uxRecursiveCallCount）记录嵌套次数，take 几次必须 give 几次才真正释放，且同样具备优先级继承
2. 必须用递归互斥量的场景：① 递归函数每一层都要访问同一共享资源；② 分层 API 中函数 A 加锁后内部又调用同样加锁的函数 B（" 锁内再调锁 "），此时普通互斥量会立即自己锁死自己
