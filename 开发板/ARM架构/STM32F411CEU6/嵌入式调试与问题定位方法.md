# 📖 引言

> 嵌入式问题定位不是 " 哪个工具最好用 "，而是 " 当前问题该走哪条流 "——日志流回答 " 运行中发生了什么 "，调试流回答 " 现场为何崩溃/卡死 "，静态分析流回答 " 代码本身有没有明显缺陷 "，方法论流保证 " 先找根因再修复 "。

# 📝 运行时观测流（日志流）

> 在非侵入或轻侵入方式下，持续记录目标运行时的行为、事件和状态。

## 实际意义

> 为什么会有该知识点？

偶发异常、长稳测试失败这类问题无法用断点捕捉，只能靠持续观测来捕获现象和行为轨迹。日志流是最低成本的 " 黑匣子 "，也是所有现场分析的第一手线索来源。

## 应用场景

> 在实际中主要被用来做什么？

- 偶发异常、长稳运行监控
- 多任务 / 中断时序混乱时的事件序列重建（SystemView 可视化）
- 丢包 / 溢出判断
- 运行时交互调试（Letter Shell 命令行）
- 崩溃前现场还原（面包屑采集）
- 为后续调试流提供定位线索

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 在关键任务边界、中断入口、错误分支埋设日志点
2. 通过非侵入通道（RTT / SWO / ITM）或轻侵入通道（串口）输出
3. 按分级过滤（DEBUG / INFO / WARN / ERROR）控制信息量
4. 异步缓冲防止日志输出阻塞业务任务
5. SystemView 通过 RTOS 钩子记录带时间戳的事件流
6. Letter Shell 将串口变成一个命令解析分发入口
7. 面包屑用环形缓冲保留崩溃前最近 N 个关键动作

## 关键公式/结论

> 最终结论和公式。

1. 日志通道按侵入性排序：RTT > SWO / ITM > 串口
2. 连接观测工具只证明通道可用，不能替代业务或实物验证
3. 当日志只能定位到 " 某处异常 " 而无法确定根因时，交接给调试流
4. 观测工具选型：要事件时序 → SystemView；要交互命令 → Letter Shell；要纯记录 → ELOG

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：搭建日志框架（ELOG / EasyLogger）

- 输出通道：默认 RTT，串口备用
- 分级过滤：DEBUG / INFO / WARN / ERROR，生产环境关 DEBUG
- 关键任务用异步输出，避免同步阻塞

```c
elog_init();
elog_set_filter_lvl(ELOG_LVL_WARN);   // 生产环境只留 WARN 以上
elog_i("task", "stack free=%u",
       uxTaskGetStackHighWaterMark(NULL));
```

### 第二步：接入 SystemView 事件追踪

- 移植 SEGGER SystemView 库，在 RTOS 中注册任务切换 / 中断钩子
- 通过 J-Link SWO 或 RTT 通道输出事件
- PC 端观察：任务切换序列、中断嵌套、CPU 占用、调度延迟
- 典型场景：定位优先级反转、调度抖动、中断耗时过长

```c
// SystemView 移植后，关键路径打点
SEGGER_SYSVIEW_PrintfHost("Sensor sample done, val=%d", adc_val);
```

### 第三步：集成 Letter Shell 命令行

- 在串口挂一个命令行 shell，把运行时变成一个可交互终端
- 注册命令：查询任务列表、读写变量、触发自检、切换运行模式

```c
// letter-shell 命令注册示例
SHELL_EXPORT_CMD(SHELL_CMD_PERMISSION(0) | SHELL_CMD_TYPE(SHELL_TYPE_CMD_FUNC),
                 status, shell_status_cmd, 查询系统状态);
// 串口输入: status
// 输出:     uptime=1234s, heap_free=5678, task_alive=3
```

### 第四步：建立面包屑崩溃采集

- 用环形缓冲记录关键事件（时间戳 + 事件码 + 关键参数），只保留最近 N 条
- HardFault 入口把面包屑与寄存器转储一起导出到日志 / Flash
- 崩溃后第一件事：读面包屑，还原 " 崩溃前最后动作序列 "

```c
// 面包屑写入（环形缓冲）
void crumb_write(uint16_t evt, uint32_t arg) {
    crumbs[head].evt = evt;
    crumbs[head].arg = arg;
    crumbs[head].tick = HAL_GetTick();
    head = (head + 1) % CRUMB_N;
}
// 崩溃后: 按环形顺序 dump 最近 16 条
```

### 第五步：SWV / ITM 调试输出

SWV（Serial Wire Viewer）是 Cortex-M 内核自带的跟踪外设，通过 **SWO 引脚（PB3 / TRACESWO）** 单线输出 trace 数据，不占用 UART、不阻塞 CPU。与 RTT 复用 SWD 不同，SWO 是独立引脚，ARM 内核原生支持。

**典型用途**：

- printf 无硬件串口输出（ITM 通道 0）
- DWT 数据观察点与 PC 采样（Profiling）
- 时间戳测量

**目标端使能**（STM32F411 示例）：

```c
// 1. 使能 TRACE 与 DWT 周期计数器
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

// 2. 解锁并配置 ITM（stimulus 端口 0）
ITM->LAR = 0xC5ACCE55;          // 写入解锁密钥
ITM->TCR = ITM_TCR_ITMENA_Msk;  // 使能 ITM
ITM->TER = 0x1;                 // 使能端口 0
```

**printf 重定向到 ITM**：

```c
int fputc(int ch, FILE *f) {
    ITM_SendChar(ch);   // CMSIS 提供的函数
    return ch;
}
```

**Keil 侧开启 SWV**：

1. Options for Target → Debug → Trace 标签
2. 勾选 Trace Enable + Serial Wire Viewer
3. 填对内核时钟（如 100 MHz）——波特率由调试器据此计算
4. 打开 View → Serial Wire Viewer 观察 ITM 输出

**注意事项**：

- SWO 引脚（PB3）若复用为 GPIO 需改回调试复用功能
- SWV 带宽有限，适合中等量级文本 / 结构化事件；超大量日志用 RTT
- ITM 输出经 TPIU 分频，内核时钟配错会导致乱码或丢包

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题 1：日志量太大导致系统卡顿

- **根因分析**：日志同步输出阻塞了关键任务；串口波特率不足或日志未做分级过滤。
- **改进方法**：改用 RTT 或异步缓冲；生产环境关闭 DEBUG 级日志；对比修改前后任务周期抖动和丢包率验证。

### 发现的问题 2：SystemView 记录后时序偏移

- **根因分析**：SystemView 事件输出本身也占通道带宽，中断过于频繁时造成观测噪声。
- **改进方法**：优先用 SWO 硬核输出；降低采样频率；只对目标任务/中断打点。

### 发现的问题 3：接入 SystemView 后日志消失 / RTT 通道忽隐忽现

- **根因分析**：elog 初始化时调用的 `SEGGER_RTT_Init()` 会 `memset` 清零整个 RTT 控制块，冲掉 SystemView 已创建的 RTT 通道（详见 [[SEGGER SystemView 移植与使用指南]] 坑点 5）。
- **改进方法**：注释掉 `elog_port.c` 中的 `SEGGER_RTT_Init()`（RTT 已由 SystemView 初始化）；elog 与 SystemView 分用不同 RTT 通道（Channel 0 / Channel 1）。

# 📝 交互式调试流（调试流）

> 通过断点、单步、寄存器和崩溃回溯，在问题发生的瞬间保留并分析现场。

## 实际意义

> 为什么会有该知识点？

崩溃、HardFault、死锁这类问题，事后看日志只能看到 " 临死前 " 的状态，必须拿到 PC / LR / PSR 和调用栈才能还原现场。调试流是拿到现场证据的唯一手段。

## 应用场景

> 在实际中主要被用来做什么？

- HardFault、栈溢出、任务死锁的现场复现
- 寄存器 / 栈分析、变量快照检查
- 断点单步排查逻辑错误
- 脱离调试器才能复现的问题（离线断点）
- RTOS 多任务各自的栈回溯

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 通过调试探针（J-Link / ST-Link / DAP-Link）附着目标芯片
2. 设置断点或在异常入口（HardFault）暂停
3. 在暂停瞬间读取寄存器（PC / LR / PSR）、调用栈和变量
4. 利用 CmBacktrace 等工具自动解析崩溃原因
5. 硬件断点（FPB / DWT）不依赖调试器持续在线，可现场驻留

## 关键公式/结论

> 最终结论和公式。

1. 区分目标板证据与主机推断，保留 ELF / AXF 和 map 文件用于离线分析
2. 断点会改变时序——" 断点调试时问题消失 " 本身就是重要线索
3. 当断点导致问题无法复现时，交接回日志流或 SystemView 等非侵入手段
4. 工具链路：J-Link（探针）→ Ozone / IDE / GDB（调试器）→ CmBacktrace（崩溃解析）

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：连接并验证 J-Link

- SWD 接四线：SWDIO、SWCLK、GND、3V3（需要日志时加 SWO）
- 用 J-Link Commander 验证连接、读寄存器、烧录

```bash
# JLinkExe 命令行（Linux/macOS；Windows 用 JLink.exe）
JLinkExe -device STM32F411CEU6 -if SWD -speed 4000
# 连接后:
#   mem32 0xE000ED00 1      → 读 SCB 基址寄存器验证连接
#   loadbin app.bin 0x08000000   → 烧录到 Flash
#   go / halt               → 运行 / 暂停
```

- 常见坑：速度过高不稳 → 降到 1000 kHz；不识别芯片 → 检查供电与复位线
- 配套工具：J-Flash（图形化烧录）、RTT Viewer（RTT 日志查看）

### 第二步：使用 Ozone 图形化调试

- 加载 `.elf` / `.axf`（与烧录固件严格一致）
- 常用视图：Source、Disassembly、Registers、Memory、Peripherals
- 断点 + 单步 + Watch 表达式
- 高级功能：Code Coverage（覆盖率）、Profiling（性能分析）、Timeline（时序）

```c
// Ozone 看外设寄存器：在 Peripherals 视图选中
// USART2->SR / TIM2->CNT 实时刷新，配合单步观察变化
```

### 第三步：IDE 单步调试

- Keil MDK：调试会话 → 断点 / Watch / 外设窗口
- VS Code + Cortex-Debug 插件（后端 J-Link / OpenOCD）

| 操作 | Keil | VS Code |
|---|---|---|
| 单步跳过 | F10 | F10 |
| 单步进入 | F11 | F11 |
| 跳出函数 | Ctrl+F11 | Shift+F11 |
| 切换断点 | F9 | F9 |

- 断点类型：行断点、条件断点（值满足才停）、数据断点（变量被写时停）
- 断点数量有限：硬件断点一般 2~6 个（Flash 片内），软件断点不限但要 RAM

### 第四步：HardFault 现场定位

- 读 `CFSR`（0xE000ED28）判断故障类型，这是定位的第一步

```c
// CFSR 常见故障位
// bit8   IBUSERR   → 取指总线错误（PC 跳到非法地址）
// bit9   PRECISERR → 精确数据总线错误（BFAR 指向出错地址）
// bit16  UNDEFINSTR→ 未定义指令
// bit17  INVSTATE  → 无效状态（跳转时 Thumb 位被清）
// bit25  DIVBYZERO → 除零（需使能）
```

- 读 `LR` 的 EXC_RETURN 判断崩溃时用哪个栈：`0xFFFFFFF9` → MSP，`0xFFFFFFFD` → PSP
- 从栈帧手工恢复调用栈：栈顶依次是 R0-R3、R12、LR、PC、xPSR
- 用 CmBacktrace 一键解析，直接打印崩溃函数调用链

### 第五步：离线断点

- 硬件断点（FPB / DWT）在 Flash 中驻留，**调试器断开后依然生效**
- 场景：崩溃只在脱离调试器运行时复现
- 触发后目标停下，再接入调试器查看现场（配合面包屑更完整）
- 注意：离线断点用硬件断点（Flash 断点），不能依赖软件断点

### 第六步：OS 异步栈回溯

- RTOS 感知调试：不仅看主栈，还能看每个任务的栈
- FreeRTOS：`uxTaskGetStackHighWaterMark()` 查栈水位、`vTaskList()` 打印任务状态
- 崩溃时通过 PSP 找到当前任务栈，恢复该任务的完整调用链
- CmBacktrace 自带 RTOS 栈回溯支持，HardFault 后直接列出任务级调用栈

#### FreeRTOS 栈水位打印

`uxTaskGetStackHighWaterMark()` 返回任务自创建以来**剩余最小栈空间**（单位：word = 4 字节），是判断任务栈是否够用的权威依据。前提是在 `FreeRTOSConfig.h` 打开宏：

```c
#define INCLUDE_uxTaskGetStackHighWaterMark   1
```

打印当前任务栈水位：

```c
void print_stack_watermark(void)
{
    UBaseType_t hwm = uxTaskGetStackHighWaterMark(NULL); // NULL = 当前任务
    uint32_t free_bytes = hwm * sizeof(StackType_t);     // word → 字节
    printf("[%s] high water: %u words (%u bytes free)\n",
           pcTaskGetName(NULL), hwm, free_bytes);
}
```

遍历打印所有任务（结构化方式，推荐）：

```c
void print_all_task_watermark(void)
{
    TaskStatus_t tasks[16];
    uint32_t count = uxTaskGetSystemState(tasks, 16, NULL);
    for (uint32_t i = 0; i < count; i++) {
        printf("Task[%s] prio=%u hwm=%u words\n",
               tasks[i].pcTaskName,
               tasks[i].uxCurrentPriority,
               tasks[i].usStackHighWaterMark);
    }
}
```

> `uxTaskGetSystemState()` / `vTaskList()` 需要 `configUSE_TRACE_FACILITY` 与 `configUSE_STATS_FORMATTING_FUNCTIONS` 均置 1；`usStackHighWaterMark` 同样以 word 为单位。

排查建议：

- hwm 趋近 0 → 任务濒临爆栈，立即加大任务栈
- 长稳测试周期性打印 hwm，取 " 运行期最小值 " 作为该任务栈的最终配置依据
- `configCHECK_FOR_STACK_OVERFLOW` 运行时栈溢出钩子可与水位打印互补

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题 1：断点调试时问题消失，无法复现

- **根因分析**：断点改变了中断时序或任务调度，时序相关 bug 对执行速度敏感。
- **改进方法**：改用 SystemView 事件追踪或 GPIO 翻转 + 逻辑分析仪，在非调试模式下复现并捕获事件序列。

### 发现的问题 2：HardFault 反汇编看到 PC 在随机地址

- **根因分析**：通常是函数指针被破坏、栈溢出覆盖了返回地址、或跳转到空指针。
- **改进方法**：先看 BFSR / MMFSR 定位总线/内存管理错误；查 MSP/PSP 栈回溯；重点检查数组越界写与任务栈大小。

### 发现的问题 3：J-Link 连接失败

- **根因分析**：SWD 引脚复用冲突、目标低功耗掉电、速度过高、复位线没接。
- **改进方法**：降到 1000 kHz 重试；确认芯片未进入 STOP/SHUTDOWN；必要时接复位线或使用 connect under reset。

### 发现的问题 4：F5 调试不停止在 main，无法源码级单步

- **根因分析**：构建配置用了 `-g0`（零调试信息），ELF 缺少 `.debug_info` / `.debug_line` 等节区，调试器无法解析符号（详见 [[05-elog日志输出与调试符号修复]]）。
- **改进方法**：Debug 构建改用 `-O0 -g3`；用 `arm-none-eabi-readelf -S <elf> | grep debug` 验证调试节区是否存在。

# 📝 静态分析与质量门禁流

> 在编码期和构建期提前发现代码缺陷、资源瓶颈和风格违规，防止问题进入运行期。

## 实际意义

> 为什么会有该知识点？

运行期问题越晚发现修复成本越高。静态分析把一部分缺陷拦截在编码和构建阶段，尤其是内存、栈这类资源问题；单元测试则把行为验证固化到每次构建里。

## 应用场景

> 在实际中主要被用来做什么？

- 编码期检查（Cppcheck、PC-lint、Coverity）
- 代码理解与复杂度评估（Understand）
- MISRA C/C++ 合规检查
- Map 文件分析（ROM / RAM / 栈估算）
- 单元测试回归防线（Unity + CMock）
- 代码审查清单

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 对源码做词法 / 语法级模式匹配，识别可疑写法
2. 构建后解析 map 文件，统计各 section 的 ROM / RAM 占用
3. Unity 通过断言 + 测试运行器，在宿主机或目标板验证函数行为
4. Understand 建立全工程调用图 / 依赖图，量化圈复杂度
5. 栈估算 + 单元测试覆盖关键算法和边界条件

## 关键公式/结论

> 最终结论和公式。

1. 静态分析可发现 " 可疑模式 "，但不能证明运行时一定正确
2. Map 估算的栈深度通常与实际有偏差，需结合运行时观测校准
3. 静态分析不能替代单元测试——MISRA 合规的代码仍可能有逻辑错误
4. 工具分工：Cppcheck 查缺陷、MISRA 查规范、Understand 查结构、Unity 查行为

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：接入 Unity 单元测试

- 对关键算法、驱动、状态机建立独立测试文件
- 结构：`setUp()` / `tearDown()` + 每个用例一个测试函数 + 运行器

```c
#include "unity.h"
void setUp(void) {}
void tearDown(void) {}

void test_ring_buffer_push_pop(void) {
    uint8_t v = 42;
    TEST_ASSERT_EQUAL(v, rb_pop(rb_push(buf, v)));
}
void test_overflow_returns_error(void) {
    TEST_ASSERT_EQUAL(RB_FULL, rb_push(full_buf, 1));
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_ring_buffer_push_pop);
    RUN_TEST(test_overflow_returns_error);
    return UNITY_END();
}
```

- 配合 CMock 对 HAL / 外设接口做 mock，实现无硬件跑测试
- 交叉编译到目标板时用串口输出结果，加入 CI 回归

### 第二步：使用 Understand 静态分析

- 建立工程并解析代码库，生成调用图 / 依赖图
- 检查分层是否违规（如驱动层反向调用应用层）
- 按圈复杂度排序，优先重构高危函数
- 内置静态检查规则，可补充自定义规则

```text
# Understand 圈复杂度视图输出示例
func             cyclomatic   lines

```

### 第三步：接入 CI 门禁

- 构建脚本加入：Unity 测试 + Cppcheck / Understand 检查，失败即中断
- 每次构建后分析 map 文件的 RAM / ROM 与栈估算，超阈值告警
- 形成 " 提交 → 单测 → 静态检查 → map 审计 " 的固定门禁链

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题 1：静态分析无告警但运行崩溃

- **根因分析**：静态分析未覆盖运行时条件（中断嵌套、堆栈溢出、硬件异常）。
- **改进方法**：静态分析发现潜在栈溢出后，用日志流或调试流在运行时验证实际栈使用峰值，复现崩溃并分析 HardFault 现场。

### 发现的问题 2：单元测试在宿主机通过，目标板跑挂

- **根因分析**：宿主机（x86）与目标板（ARM）的 int/指针宽度、对齐、端序不同；或 mock 的时序与真实硬件不一致。
- **改进方法**：关键代码交叉编译到目标板跑一遍测试；mock 只用于无硬件环境，硬件相关逻辑单独做板级验证。

# 📝 系统化调试方法论流

> 统摄前三类工具的流程纪律，要求 " 先根因调查，后单点修复，再回归验证 "。落地时直接套用 [[嵌入式系统诊断流程模板]]。

## 实际意义

> 为什么会有该知识点？

工具用得再好，缺少流程纪律也会 " 修一个坑、埋一个坑 "。方法论流保证定位、修复、验证的闭环可重复。

## 应用场景

> 在实际中主要被用来做什么？

- 任何技术问题的完整处理流程
- 多次修复无效或越修越乱的问题
- 跨模块问题责任边界不清时

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 根因调查：仔细读错误信息、稳定复现、检查近期变更、逐层采集证据
2. 模式分析：找同类工作代码、对比差异、理解依赖
3. 假设与测试：一次只验证一个假设，最小改动
4. 修复与验证：先写失败用例，再做单点修复，回归验证

## 关键公式/结论

> 最终结论和公式。

1. 红线一：未找到根因前禁止修复
2. 红线二：3 次以上修复失败要质疑架构，而不是继续试第 4 个补丁
3. 95% 的 " 无根因 " 案例都是调查不完整
4. 方法模板：流程落地直接套用 [[嵌入式系统诊断流程模板]]（问题描述 → 原因分析 → 设计实验 → 验证实验）

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：建立问题模板

> 方法模板直接使用 [[嵌入式系统诊断流程模板]]——方法论四阶段与模板四部分一一对应：

| 方法论四阶段   | 诊断模板对应章节                                     |
| -------- | -------------------------------------------- |
| 1. 根因调查  | 一、问题的描述（表现 / 复现路径 / 正常预期）+ 二、初步 checklist 排查 |
| 2. 模式分析  | 二、提出可能的问题                                    |
| 3. 假设与测试 | 三、设计实验验证猜想                                   |
| 4. 修复与验证 | 四、验证实验（环境 / 步骤 / 结果 / 分析）                    |

- 问题描述固定为：现象 → 复现路径 → 正常预期 → 证据 → 假设 → 修复 → 验证
- 模板内置 11 项初步 checklist，按序快速排除常见原因：硬件问题、程序爆栈、过度优化（优化等级降 0）、死循环、函数返回值错误、空指针、API 用错（FreeRTOS 应用其自带 API）、代码段未执行、线程被饿死（加 vTaskDelay）、线程无 while(1)、互斥量 / 信号量死锁

### 第二步：严格执行四阶段

根因调查 → 模式分析 → 假设与测试 → 修复与验证，一次只验证一个假设。

### 第三步：固化证据

重大问题强制保留现场截图 / 日志 / 寄存器转储 / 面包屑；回归测试通过且问题 3 次以上稳定不复现才算关闭。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题：修复后老问题反复出现

- **根因分析**：之前的修复对症未对根，缺乏系统化方法，只修复了表面现象。
- **改进方法**：按四阶段法重新调查，建立失败用例；回归验证通过且 3 次以上稳定不复现。

# 💬 Q&A

> 自问自答，检验理解深度。按难度递进排列。

## 🟢 基础

> 最基本的概念和用法，入门必知。

### Q1：日志流和调试流如何取舍？

A1：能复现且需要看现场 → 调试流；不能频繁复现或需要长稳观察 → 日志流。判断依据：调试流侵入性强（断点会改变时序），日志流信息密度低。

### Q2：四条流分别是什么，何时用？

A2：日志流（运行期 / 长稳，低侵入）、调试流（崩溃 / 死锁 / HardFault，高侵入）、静态分析流（编码期 / 构建期，无侵入）、方法论流（全周期，流程纪律）。任何问题都必须服从方法论流。

## 🟡 进阶

> 容易踩的坑和常见误区。

### Q3：静态分析能替代单元测试吗？

A3：不能。静态分析检查代码模式，单元测试验证运行时行为。MISRA 合规的代码仍可能有逻辑错误，两者是互补关系。

### Q4：断点调试时问题消失是怎么回事？

A4：断点改变了中断时序或任务调度，说明这是时序敏感 bug。应改用 SystemView 事件追踪或 GPIO 翻转 + 逻辑分析仪，在非调试模式下复现。

### Q5：RTT 和串口日志如何选？

A5：RTT 非侵入、速度高（依赖 J-Link），适合高频日志和 SystemView 事件；串口独立于调试器、可脱离调试器跑，适合量产诊断和远程采集。选型看目标系统是否有 J-Link 常驻。

## 🔴 困难

> 结合实战的深层原理和设计权衡。

### Q6：如何量化日志对系统性能的影响？

A6：对比开关日志前后的任务周期抖动、CPU 占用和丢包率。不同输出通道（RTT / 串口 / SWO）开销差异大，用 SystemView 或定时 GPIO 翻转测量。

### Q7：RTOS 任务栈应该设置多大？

A7：先用静态分析估算（map 文件栈估算），再用运行时水位标记校准（`uxTaskGetStackHighWaterMark`）。需综合考虑任务调用深度、中断嵌套、局部变量大小。

### Q8：HardFault 时如何判断用 MSP 还是 PSP 回溯？

A8：读崩溃时 LR 中的 EXC_RETURN：`0xFFFFFFF9` 表示线程模式用 MSP，`0xFFFFFFFD` 表示线程模式用 PSP。RTOS 下任务通常跑在 PSP，所以任务栈回溯要取 PSP；中断嵌套在 Handler 模式取 MSP。

# 📋 总结

嵌入式调试与问题定位的核心是 " 选对路 "，而不是 " 用好一个工具 "。四条流各司其职：日志流（ELOG / SystemView / Letter Shell / 面包屑）低侵入、适合长稳和偶发问题；调试流（J-Link / Ozone / IDE 单步 / HardFault / 离线断点 / OS 栈回溯）高侵入、适合崩溃和死锁现场；静态分析流（Unity / Understand / Cppcheck）无侵入、在编码期预防；方法论流贯穿全程，保证先根因后修复。组合原则是：日志流捕获现象，调试流定位现场，静态分析防止复发，方法论流保证流程可重复。
