# 📖 引言

> 嵌入式问题定位不是"哪个工具最好用"，而是"当前问题该走哪条流"——日志流回答"运行中发生了什么"，调试流回答"现场为何崩溃/卡死"，静态分析流回答"代码本身有没有明显缺陷"，方法论流保证"先找根因再修复"。

---

# 📝 运行时观测流（日志流）

> 在非侵入或轻侵入方式下，持续记录目标运行时的行为、事件和状态。

## 实际意义

> 为什么会有该知识点？

偶发异常、长稳测试失败这类问题无法用断点捕捉，只能靠持续观测来捕获现象和行为轨迹。日志流是最低成本的"黑匣子"，也是所有现场分析的第一手线索来源。

## 应用场景

> 在实际中主要被用来做什么？

- 偶发异常、长稳运行监控
- 多任务 / 中断时序混乱时的事件序列重建
- 丢包 / 溢出判断
- 为后续调试流提供定位线索

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 在关键任务边界、中断入口、错误分支埋设日志点
2. 通过非侵入通道（RTT / SWO / ITM）或轻侵入通道（串口）输出
3. 按分级过滤（DEBUG / INFO / WARN / ERROR）控制信息量
4. 异步缓冲防止日志输出阻塞业务任务

```c
// ELOG 分级日志示例
elog_init();
elog_set_filter(ELOG_LVL_WARN);   // 生产环境只留 WARN 以上
elog_i("task", "Task started, stack free=%u",
       uxTaskGetStackHighWaterMark(NULL));
```

## 关键公式/结论

> 最终结论和公式。

1. 日志通道按侵入性排序：RTT > SWO / ITM > 串口
2. 连接观测工具只证明通道可用，不能替代业务或实物验证
3. 当日志只能定位到"某处异常"而无法确定根因时，交接给调试流

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：选择输出通道

按项目场景选 RTT（默认推荐，非侵入）或串口（简单通用，注意波特率）。

### 第二步：配置日志分级与异步缓冲

配置 ELOG 分级过滤，关键任务开启异步输出缓冲，避免同步阻塞。

### 第三步：埋点

在任务边界、中断入口、错误分支加日志，带上时间戳和上下文（任务名、栈水位）。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题

日志量太大导致系统卡顿。

### 根因分析

日志同步输出阻塞了关键任务；串口波特率不足或日志未做分级过滤。

### 改进方法

改用 RTT 或异步缓冲；生产环境关闭 DEBUG 级日志；对比修改前后任务周期抖动和丢包率验证。

# 📝 交互式调试流（调试流）

> 通过断点、单步、寄存器和崩溃回溯，在问题发生的瞬间保留并分析现场。

## 实际意义

> 为什么会有该知识点？

崩溃、HardFault、死锁这类问题，事后看日志只能看到"临死前"的状态，必须拿到 PC / LR / PSR 和调用栈才能还原现场。

## 应用场景

> 在实际中主要被用来做什么？

- HardFault、栈溢出、任务死锁的现场复现
- 寄存器 / 栈分析
- 崩溃回溯（CmBacktrace）
- 关键变量快照检查

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 通过调试探针（GDB + OpenOCD、J-Link / Ozone）附着目标芯片
2. 设置断点或在异常入口（HardFault）暂停
3. 在暂停瞬间读取寄存器（PC / LR / PSR）、调用栈和变量
4. 利用 CmBacktrace 等工具自动解析崩溃原因

```c
// HardFault 现场需要记录的三个核心寄存器
// PC   → 崩溃发生时的指令地址
// LR   → 返回地址，定位调用来源
// PSR  → 状态寄存器，含异常编号位
```

## 关键公式/结论

> 最终结论和公式。

1. 区分目标板证据与主机推断，保留 ELF / AXF 和 map 文件用于离线分析
2. 断点会改变时序——"断点调试时问题消失"本身就是重要线索
3. 当断点导致问题无法复现时，交接回日志流或 SystemView 等非侵入手段

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：保留构建产物

保存 ELF / AXF、map、hex / bin 文件，确保与烧录的固件一致。

### 第二步：配置调试环境

配置 GDB / OpenOCD 或 J-Link Ozone，开启 CmBacktrace 或 RTOS 插件。

### 第三步：复现并抓现场

稳定复现崩溃，在 HardFault 入口暂停，记录 PC / LR / PSR、调用栈和关键变量。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题

断点调试时问题消失，无法复现。

### 根因分析

断点改变了中断时序或任务调度，时序相关 bug 对执行速度敏感。

### 改进方法

改用 SystemView 事件追踪或 GPIO 翻转 + 逻辑分析仪，在非调试模式下复现并捕获事件序列。

# 📝 静态分析与质量门禁流

> 在编码期和构建期提前发现代码缺陷、资源瓶颈和风格违规，防止问题进入运行期。

## 实际意义

> 为什么会有该知识点？

运行期问题越晚发现修复成本越高。静态分析把一部分缺陷拦截在编码和构建阶段，尤其是内存、栈这类资源问题。

## 应用场景

> 在实际中主要被用来做什么？

- 编码期检查（Cppcheck、PC-lint、Coverity）
- MISRA C/C++ 合规检查
- Map 文件分析（ROM / RAM / 栈估算）
- 单元测试（Unity / CMock）
- 代码审查清单

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 对源码做词法 / 语法级模式匹配，识别可疑写法
2. 构建后解析 map 文件，统计各 section 的 ROM / RAM 占用
3. 通过栈估算 + 单元测试覆盖关键算法和边界条件

```c
// 常见静态分析告警示例
// Cppcheck:  "Buffer 'buf' may be accessed with index out of bounds"
// MISRA:     "Rule 10.1: Operands shall not be of an inappropriate
//             essential type"
```

## 关键公式/结论

> 最终结论和公式。

1. 静态分析可发现"可疑模式"，但不能证明运行时一定正确
2. Map 估算的栈深度通常与实际有偏差，需结合运行时观测校准
3. 静态分析不能替代单元测试——MISRA 合规的代码仍可能有逻辑错误

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：接入 CI 门禁

在 CI / 构建脚本中加入 Cppcheck / MISRA 检查，失败即中断。

### 第二步：分析 map 文件

每次构建后分析 RAM / ROM 占用和栈估算，超阈值告警。

### 第三步：补充单元测试

用 Unity 覆盖关键算法和边界条件，形成回归防线。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题

静态分析无告警但运行崩溃。

### 根因分析

静态分析未覆盖运行时条件（中断嵌套、堆栈溢出、硬件异常）。

### 改进方法

静态分析发现潜在栈溢出后，用日志流或调试流在运行时验证实际栈使用峰值，复现崩溃并分析 HardFault 现场。

# 📝 系统化调试方法论流

> 统摄前三类工具的流程纪律，要求"先根因调查，后单点修复，再回归验证"。

## 实际意义

> 为什么会有该知识点？

工具用得再好，缺少流程纪律也会"修一个坑、埋一个坑"。方法论流保证定位、修复、验证的闭环可重复。

## 应用场景

> 在实际中主要被用来做什么？

- 任何技术问题的完整处理流程
- 多次修复无效或越修越乱的问题
- 跨模块问题责任边界不清时

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 根因调查：仔细读错误信息、稳定复现、检查近期变更、逐层采集证据
2. 模式分析：找同类工作代码、对比差异、理解依赖
3. 假设与测试：一次只验证一个假设，最小改动
4. 修复与验证：先写失败用例，再做单点修复，回归验证

## 关键公式/结论

> 最终结论和公式。

1. 红线一：未找到根因前禁止修复
2. 红线二：3 次以上修复失败要质疑架构，而不是继续试第 4 个补丁
3. 95% 的"无根因"案例都是调查不完整

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：建立问题模板

固定格式：现象 → 复现步骤 → 证据 → 假设 → 修复 → 验证。

### 第二步：严格执行四阶段

根因调查 → 模式分析 → 假设与测试 → 修复与验证，一次只验证一个假设。

### 第三步：固化证据

重大问题强制保留现场截图 / 日志 / 寄存器转储；回归测试通过且问题 3 次以上稳定不复现才算关闭。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题

修复后老问题反复出现。

### 根因分析

之前的修复对症未对根，缺乏系统化方法，只修复了表面现象。

### 改进方法

按四阶段法重新调查，建立失败用例；回归验证通过且 3 次以上稳定不复现。

# 💬 Q&A

> 自问自答，检验理解深度。按难度递进排列。

## 🟢 基础

> 最基本的概念和用法，入门必知。

### Q1：日志流和调试流如何取舍？

A1：能复现且需要看现场 → 调试流；不能频繁复现或需要长稳观察 → 日志流。判断依据：调试流侵入性强（断点会改变时序），日志流信息密度低。

### Q2：四条流分别是什么，何时用？

A2：日志流（运行期 / 长稳，低侵入）、调试流（崩溃 / 死锁 / HardFault，高侵入）、静态分析流（编码期 / 构建期，无侵入）、方法论流（全周期，流程纪律）。任何问题都必须服从方法论流。

## 🟡 进阶

> 容易踩的坑和常见误区。

### Q3：静态分析能替代单元测试吗？

A3：不能。静态分析检查代码模式，单元测试验证运行时行为。MISRA 合规的代码仍可能有逻辑错误，两者是互补关系。

### Q4：断点调试时问题消失是怎么回事？

A4：断点改变了中断时序或任务调度，说明这是时序敏感 bug。应改用 SystemView 事件追踪或 GPIO 翻转 + 逻辑分析仪，在非调试模式下复现。

## 🔴 困难

> 结合实战的深层原理和设计权衡。

### Q5：如何量化日志对系统性能的影响？

A5：对比开关日志前后的任务周期抖动、CPU 占用和丢包率。不同输出通道（RTT / 串口 / SWO）开销差异大，用 SystemView 或定时 GPIO 翻转测量。

### Q6：RTOS 任务栈应该设置多大？

A6：先用静态分析估算（map 文件栈估算），再用运行时水位标记校准（`uxTaskGetStackHighWaterMark`）。需综合考虑任务调用深度、中断嵌套、局部变量大小。

# 📋 总结

嵌入式调试与问题定位的核心是"选对路"，而不是"用好一个工具"。四条流各司其职：日志流低侵入、适合长稳和偶发问题；调试流高侵入、适合崩溃和死锁现场；静态分析无侵入、在编码期预防；方法论流贯穿全程，保证先根因后修复。组合原则是：日志流捕获现象，调试流定位现场，静态分析防止复发，方法论流保证流程可重复。
