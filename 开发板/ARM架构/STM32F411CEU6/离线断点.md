# 📖 引言

> 离线断点 = **驻留在芯片调试硬件里的断点，调试器断开连接后依然生效**。它专治 " 只有脱离调试器才复现 " 的 bug：目标自由运行时撞上断点自己停住，再接入调试器读取现场。要彻底理解它，必须打通 Cortex-M 断点体系的五块拼图——FPB（指令断点 + Flash Patch）、DWT（数据观察点）、内联断点（BKPT 指令）、重映射（不重烧改代码），以及 MPU（" 调试正常、离线就崩 " 的头号元凶）。

---

# 📝 知识点 1：FPB 断点 —— 指令硬件断点，离线断点的核心载体

> FPB（Flash Patch and Breakpoint Unit）是 Cortex-M 内核自带的一组**硬件比较器**，把 PC 与预设地址逐周期比较，命中即暂停内核。它长在芯片里，不依赖调试器在线，这就是离线断点的本质。

## 实际意义

> 为什么会有该知识点？

调试器设置断点有两种：**软件断点**临时把 Flash 里的指令改写成 `BKPT`，调试器一断开就把 Flash 内容还原，断点随之消失；**硬件断点**由 FPB 比较器实现，状态保存在芯片寄存器里，只要不掉电就一直在。而现实中大量 bug（时序敏感、中断竞争、MPU 权限）只在**脱离调试器**运行时才暴露——接上调试器它就正常。唯一能在这种场景下 " 守株待兔 " 的，就是 FPB 硬件断点。

## 应用场景

> 在实际中主要被用来做什么？

- 崩溃只在脱离调试器运行时复现——目标自由跑，撞断点自停
- 长稳测试中让目标在异常点停车，保留现场供后续接入分析
- 不占用 RAM、不改写 Flash 内容，对目标零污染

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. FPB 提供 **6 个指令比较器**（COMP0-5），每个可独立使能
2. 内核每次取指时，FPB 硬件并行比较 PC 与各比较器地址
3. 命中 → 产生 Debug Event → 内核 **halt**，时钟冻结、状态保留
4. 调试器断开后比较器内容仍在寄存器中，SWD 重新连接即可接管现场
5. F411（Cortex-M4F）FPB 基地址 `0xE0002000`，还附带 2 个 patch 比较器（见知识点 4）

```c
// FPB 寄存器操作（CMSIS）——原理演示，实际调试多用调试器 GUI 设置
FPB->CTRL = FPB_CTRL_ENABLE_Msk;                    // 使能 FPB
FPB->COMP[0] = ((uint32_t)&buggy_func & ~1UL)
             | FPB_COMP_ENABLE_Msk;                 // 对 buggy_func 设硬件断点
```

## 关键公式/结论

> 最终结论和公式。

1. **离线断点必须用 FPB 硬件断点，不能用软件断点**——软件断点依赖调试器在线改写 Flash
2. 断点配额有限：M4 只有 **6 个指令断点**（+2 个 patch），不够时合并断点或改用 DWT PC 匹配
3. 指令断点地址按**半字（2 字节）对齐**，实际使用时通常按 4 字节对齐放置
4. 掉电 / 复位后 FPB 配置清空，离线断点需在断开的会话中重新设置

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：在调试器里设置硬件断点

Ozone：在目标函数 / 汇编行右键 → `Toggle Breakpoint`，确认断点类型为 **Hardware**（非 Flash/Software）。

Keil：直接在行号处 F9，硬件断点资源自动使用 FPB。

### 第二步：断开调试器，让目标自由运行

- Ozone 中点 `Stop Debugging`（或直接拔线），目标脱离调试器独立运行
- 此刻不要断电——FPB 比较器靠目标供电维持

### 第三步：触发后重新接入，读取现场

- 目标撞上断点自行 halt
- 重新连接调试器，直接停在断点处，此时可读寄存器、调用栈、全局变量
- 配合面包屑（环形缓冲）可还原 " 停住前最后动作序列 "

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题：离线断点设置后目标完全不停

- **根因分析**：断点设成了软件断点（Flash Breakpoint），调试器断开时 Flash 补丁被还原；或目标掉电后 FPB 配置丢失；或断点地址 2 字节对齐不符合。
- **改进方法**：确认断点类型为 Hardware；保持目标供电；重新设置断点后先验证一次在线触发正常，再断开。

# 📝 知识点 2：DWT 断点 —— 数据观察点，抓 " 谁动了我的变量 "

> DWT（Data Watchpoint and Trace）提供 **4 个数据比较器**，监视某个地址 / 地址段的**读、写访问**。FPB 回答 " 执行到哪 "，DWT 回答 " 谁碰了这个地址 "。

## 实际意义

> 为什么会有该知识点？

很多 " 离线才复现 " 的 bug 不是崩在执行路径上，而是**数据被悄悄写坏**（数组越界、野指针、DMA 与 CPU 竞争同一 buffer），最终崩在毫不相干的另一处。事后看代码找不到写入方——DWT 数据观察点能把 " 谁改了这个变量 " 当场按住。

## 应用场景

> 在实际中主要被用来做什么？

- 全局变量被意外修改，定位写入方（函数 / ISR / DMA）
- 数组越界写、栈破坏、buffer 被两个外设竞争
- 硬件断点配额用尽时，把 DWT 比较器配置成 PC 匹配，扩充指令断点数量
- 离线驻留：监视量产中变量是否被异常改写

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. 4 个比较器 `COMP0-3` + 掩码寄存器 `MASK0-3`
2. `FUNCTION` 寄存器配置触发条件：**任意访问 / 数据读 / 数据写**
3. `MASK` 把单地址监视扩展成 `2^N` 字节的地址段监视（如 N=4 → 16 字节段）
4. 命中 → Debug Event → halt，与 FPB 独立，可同时使用
5. 与 FPB 一样是芯片硬件外设，调试器断开后驻留生效

```c
// DWT 数据观察点：监视 g_status 被"写"时停下
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;      // 使能调试跟踪
DWT->COMP[0] = (uint32_t)&g_status;                  // 目标变量地址
DWT->MASK[0] = 0;                                    // 0 → 精确匹配单地址
DWT->FUNCTION[0] = (1UL << DWT_FUNCTION_FUNCTION_Pos)   // 0b001 = MATCHED
                 | (1UL << DWT_FUNCTION_DATAVADDR1_Pos); // DATAVADDR=0b10 → 数据写
```

## 关键公式/结论

> 最终结论和公式。

1. **监视范围 = 2^MASK 字节**，MASK=0 表示精确单地址
2. 数据观察点看的是**数据访问**，不占 FPB 指令断点配额
3. 触发条件三选一：任意 / 读 / 写；写监视最能抓 " 变量被改坏 "
4. DWT 比较器也可配成 PC 比较器，变相增加硬件断点数量

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：Ozone 添加数据观察点

在 Watch 窗口右键 `g_status` → `Add Data Watchpoint`，或在断点窗口新建 Data Breakpoint，填入变量名与访问类型（Read / Write / Both）。

### 第二步：配置地址段监视（可选）

监视一段 buffer（如 DMA 目标区）时，在寄存器窗口直接改 `DWT_MASK0`：要监视 256 字节就设 `MASK0=8`（2^8）。

### 第三步：离线运行验证

同知识点 1：断开调试器 → 自由运行 → 变量被写瞬间 halt → 重连看现场（此时调用栈顶就是写入方）。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题：数据观察点设了但不停

- **根因分析**：`DEMCR.TRCENA` 未置位，DWT 未使能；或 FUNCTION 触发类型配错（要抓写却配了读）；或变量被优化掉没有实际内存地址。
- **改进方法**：确认 `CoreDebug->DEMCR |= TRCENA`；把触发条件改成 Read/Write 都试一次；用 `volatile` 修饰变量防止被优化；在 map 文件确认变量实际地址。

# 📝 知识点 3：内联断点 —— BKPT 指令，把断点写进代码

> 内联断点是用 **`BKPT` 指令**把断点直接写进源码：执行到这条指令时内核产生调试事件。它是 " 代码即断点 "，不依赖调试器、不依赖 ELF 符号。

## 实际意义

> 为什么会有该知识点？

调试器设的断点绑定当前工程和符号表，固件一换就没了；内联断点**随固件走**，现场烧什么固件就有对应的停点。适合必须在特定路径硬停、或者现场没有工程师调试的场景——甚至可以在量产固件里通过宏保留诊断停点。

## 应用场景

> 在实际中主要被用来做什么？

- 关键路径（错误分支、断言失败处）插入硬停点，配合面包屑抓现场
- 现场测试人员触发异常路径后，把停在现场的板子寄回 / 交给工程师
- 结合 DebugMonitor 异常：断点命中不 halt，而是进异常保存现场后继续跑

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. `BKPT #imm` 编译为 16 位指令 `0xBE00 | imm`
2. 执行时产生 Debug Event，行为取决于**是否有调试器 / 是否使能 DebugMonitor**：

```text
BKPT 执行
   ├─ 调试器在线       → 暂停内核（当作断点）
   ├─ 无调试器 + DebugMonitor 未使能 → 触发 HardFault ⚠
   └─ 无调试器 + DebugMonitor 使能   → 进入 DebugMon_Handler，可自定义处理
```

3. 因此裸用 BKPT 做 " 离线断点 " 有陷阱——**没有调试器时默认会 HardFault**，必须配合 DebugMonitor 异常才安全
4. BKPT 是 16 位指令，属于侵入式手段，会改变执行时序

```c
__BKPT(0);                        // CMSIS 内建函数，等价于内联汇编
// 或：__asm volatile ("BKPT #0");

// 配合 DebugMonitor 异常，实现"停点 → 存现场 → 继续"的离线诊断
void DebugMon_Handler(void) {
    crumb_write(EVT_BP_HIT, (uint32_t)&my_func);   // 记录命中点
    // 存关键变量、寄存器到日志 / Flash，然后返回继续执行
}
```

## 关键公式/结论

> 最终结论和公式。

1. **BKPT ≠ FPB 硬件断点**：无调试器时 BKPT 默认触发 HardFault，不是真正的离线断点
2. 内联断点随固件走，发布前必须用宏隔离或移除
3. DebugMonitor 异常需在 `SCB->SHCSR` 使能 `DEBUGMONENA_Msk`，并将它配为最低优先级以避免阻塞关键中断

```c
// 发布 / 离线诊断双模式宏隔离
#ifdef DEBUG_OFFLINE_BREAK
    #define BP()  __BKPT(0)
#else
    #define BP()  do {} while (0)
#endif
```

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：在目标位置插入断点

```c
if (sensor_read() != OK) {
    BP();                        // 这里停一下
}
```

### 第二步：使能 DebugMonitor（离线安全前提）

```c
SCB->SHCSR |= SCB_SHCSR_DEBUGMONENA_Msk;   // 使能 DebugMonitor 异常
NVIC_SetPriority(DebugMonitor_IRQn, 15);   // 最低优先级，避免干扰业务
```

### 第三步：在线验证后断开实测

先在调试器下确认能停，再断开调试器运行：此时应进入 `DebugMon_Handler`（而不是 HardFault），面包屑记录命中点。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题：代码里有 BKPT，断开调试器后直接 HardFault

- **根因分析**：DebugMonitor 异常未使能，BKPT 在无调试器时产生 HardFault；或 DebugMonitor 优先级太低被同级中断顶掉。
- **改进方法**：确认 `SCB->SHCSR.DEBUGMONENA` 置位；确认 DebugMonitor 中断处理函数有实现（否则进 Default_Handler 死循环）；生产固件用宏关掉所有 BKPT。

# 📝 知识点 4：重映射 —— FPB 的 Flash Patch 功能，不重烧也能改代码

> FPB 有两个身份：**断点** + **Flash Patch（重映射）**。2 个 patch 比较器把 CPU 对 Flash 特定地址的取指 / 取字，**重定向到 RAM 里的替换代码**——现场打补丁，不用重新烧录 Flash。

## 实际意义

> 为什么会有该知识点？

现场固件有 bug，重新烧录有现实障碍：量产设备量大、远程无法插线、Flash 被 RDP 读保护锁死、或者只是不想为一条指令的修改冒擦写风险。Flash Patch 让 " 用 RAM 里的修复指令顶替 Flash 里的坏指令 " 成为可能——**停机检修时把补丁代码放 RAM，配置重映射即可**。

## 应用场景

> 在实际中主要被用来做什么？

- 现场只改一两条指令 / 一个常量就能绕过的 bug
- 只读 Flash / 熔丝保护（RDP 高等级）下无法重烧时的紧急修复
- 把跳变频繁的字面量池（常量）重映射到 RAM，提升访问性能（配合 Cache 策略）

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. `FPB->REMAP` 寄存器保存 RAM 补丁区**基地址（32 字节对齐）**
2. patch 比较器（COMP6/7）保存要匹配的 Flash 地址
3. 命中时，CPU 对该地址的访问**改走 RAM 基址 + 原地址低 5 位偏移**
4. 映射单位是 **32 字节块**——整块替换，补丁代码要组织成 32 字节对齐的替换块
5. 掉电 / 复位后配置丢失，需由 Bootloader 或调试器在每次启动时重新加载

```c
// FPB Flash Patch：把 Flash 中 bad_instr 处的指令替换为 RAM 中的补丁
static uint8_t patch_ram[32] __attribute__((aligned(32)));  // 补丁块，32B 对齐

FPB->REMAP  = (uint32_t)patch_ram;          // 补丁 RAM 基址
FPB->COMP[6] = ((uint32_t)&bad_instr & ~1UL)
             | FPB_COMP_ENABLE_Msk;         // 匹配 Flash 中的坏指令地址
```

## 关键公式/结论

> 最终结论和公式。

1. **重映射单位 = 32 字节块**，补丁区必须 32 字节对齐（低 5 位为 0）
2. 每次复位需重新配置（配置掉电丢失）
3. patch 与断点**共用 FPB 硬件**：M4 的 "6+2" 即 6 个指令断点 + 2 个 patch 比较器
4. 与链接期 " 重定位（relocation）" 是两回事：relocation 改 LMA/VMA 搬运代码，remap 是硬件运行时替换取指目标

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：编译出补丁代码并放进 RAM

把修复函数放到 32 字节对齐的 RAM 段（GCC：`__attribute__((section(".patch")))`），或直接调试器里往 RAM 写机器码。

### 第二步：配置 REMAP + 比较器

按上述代码设置 `FPB->REMAP` 与 `FPB->COMP[6]`，使能 FPB。

### 第三步：验证

单步执行到 `bad_instr`，观察 PC 是否跳转到 RAM 补丁区；确认替代逻辑生效后，用相同方式补下一条坏指令。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题：重映射没生效，还是执行了 Flash 原指令

- **根因分析**：RAM 补丁区未 32 字节对齐；REMAP 基址低 5 位非 0；比较器地址与指令实际地址差一（Thumb 位 / 地址对齐）；或 FPB 使能位没开。
- **改进方法**：用 `(uint32_t)patch_ram & 0x1F` 检查对齐；比较器写入 `addr & ~1`；确认 `FPB->CTRL.ENABLE` 置位；断点与 patch 不要同时命中同一地址。

# 📝 知识点 5：MPU —— " 调试正常、离线就崩 " 的头号元凶

> MPU（Memory Protection Unit）给内存区域配置访问权限（读 / 写 / 执行）。它最关键的调试属性是：**调试器通过 AHB-AP（DAP）访问内存，绕开内核总线，不经过 MPU 校验**——所以 MPU 配置错了，调试器下一切正常，真机一跑就 MemManage Fault / HardFault。

## 实际意义

> 为什么会有该知识点？

" 接上调试器就正常，拔掉就死机 " 是嵌入式调试的头号玄学。除了断点改变时序，**MPU 权限配置错误**是另一个经典根因，且隐蔽性更强：调试器访问不触发违规，掩盖了真实权限问题。排查离线崩溃时，必须把 MPU 当作高嫌疑对象。

## 应用场景

> 在实际中主要被用来做什么？

- 程序意外写入只读区 / 数据区执行指令 → 用 MPU 权限位暴露违规
- 栈 / 堆越界 → 用 MPU 区域卡住边界，越界即 Fault
- 调试器下正常但真机崩溃 → 系统排查 MPU 配置
- 禁止执行（XN）区域 → 防止数据区被当代码执行（安全加固）

## 核心逻辑/原理

> 它是如何工作的？拆解背后的机制。

1. **8 个可编程区域**（F411），每区域由 RBAR（基址）+ RASR（属性）描述
2. 属性 = 大小（2^N）、访问权限（AP 位）、缓存属性（TEX/C/B）、XN 禁止执行
3. 每区域含 **8 个子区域**，可单独禁用（如用 8 个子区域拼大区域边界）
4. 区域重叠时**区域号大者优先**
5. 访问违规 → MemManage Fault → 默认上升为 HardFault
6. 调试器访问（AHB-AP）**不经过内核总线，不触发 MPU 违规** → 离线才暴露

```c
// MPU 配置示例：把 g_secret 设为"特权可读写、用户不可访问、禁止执行"
MPU->RNR  = 0;                                     // 选区域 0
MPU->RBAR = (uint32_t)&g_secret & ~0x1F;           // 基址，对齐到区域大小
MPU->RASR = MPU_RASR_ENABLE_Msk                    // 使能本区域
          | (1u << MPU_RASR_AP_Pos)                // AP=0b001：仅特权可读写
          | MPU_RASR_XN_Msk                        // 禁止执行
          | (5u << MPU_RASR_SIZE_Pos);             // 大小 = 2^5 = 32 B
MPU->CTRL = MPU_CTRL_ENABLE_Msk;                   // 全局使能 MPU
```

## 关键公式/结论

> 最终结论和公式。

1. **区域大小 = 2^SIZE**（最小 32 字节），基址必须对齐到区域大小
2. 调试器访问绕过 MPU → **" 调试正常、离线崩 " 优先查 MPU 配置**
3. MemManage 可经 `SCB->SHCSR.MEMFAULTENA` 独立使能；违规详情在 `MMFSR`，违规地址在 `MMFAR`
4. 与断点配合：MPU 违规能**先于数据被彻底破坏**暴露内存问题，比事后追查效率更高

## 实际操作步骤

> 动手验证/配置的具体操作。

### 第一步：确认故障类型

离线复现 HardFault 后，读 `CFSR`（0xE000ED28）判断是否 MemManage：`bit0 IACCVIOL`（取指违规）/ `bit1 DACCVIOL`（数据访问违规）/ `bit2 MSTKERR`（入栈违规）。

```c
uint32_t cfsr = SCB->CFSR;
if (cfsr & SCB_CFSR_MEMFAULTSR_Msk) {
    // 是 MPU 违规，读 MMFAR 拿违规地址
    uint32_t bad_addr = SCB->MMFAR;
}
```

### 第二步：对照 MMFAR 排查 MPU 区域

拿违规地址对照 RBAR/RASR 表，检查：是否落在未配置区域（默认不使能 MPU 时无保护，使能后未配置区域访问即违规）、AP 权限是否过严、XN 是否误设。

### 第三步：缩小范围复现

逐个禁用 MPU 区域，找到触发违规的那一个；确认后修正区域属性，重新做离线回归。

## 常见问题

> 现象 → 根因 → 修复。

### 发现的问题：使能 MPU 后程序立刻 HardFault

- **根因分析**：未配置区域的访问全部违规——常见于中断向量表 / 外设寄存器区未显式配置；或区域大小 / 对齐不满足 2^N 规则导致配置无效。
- **改进方法**：先配置一个覆盖全地址空间的背景区域（AP=全权限），再叠加具体保护区域；用 `MPU->CTRL.HFNMIENA` 决定 HardFault 入口是否也受 MPU 约束；逐步使能区域定位冲突。

# 💬 Q&A

> 自问自答，检验理解深度。按难度递进排列。

## 🟢 基础

> 最基本的概念和用法，入门必知。

### Q1：离线断点是什么？为什么需要它？

A1：离线断点是驻留在芯片调试硬件（FPB/DWT）中的断点，调试器断开后依然生效。需要它的原因是大量 bug 只在脱离调试器运行时才复现——接上调试器它就正常。离线断点让目标自由运行时撞上断点自行停下，再接入调试器读取现场。

### Q2：硬件断点和软件断点有什么区别？

A2：硬件断点用 FPB 比较器实现，驻留芯片、断开调试器仍生效、不改 Flash 内容，但数量有限（M4 仅 6 个）；软件断点由调试器临时把 Flash 指令改写为 BKPT，断开即还原，数量不限但依赖调试器在线。

## 🟡 进阶

> 容易踩的坑和常见误区。

### Q3：BKPT 内联断点能当离线断点用吗？

A3：不能直接用。BKPT 执行时如果没有调试器且 DebugMonitor 异常未使能，会触发 HardFault 而不是 " 停车等待 "。要做安全的离线停点，需使能 `SCB->SHCSR.DEBUGMONENA` 并提供 `DebugMon_Handler`，否则默认行为是 HardFault。

### Q4：数据观察点和普通断点有什么区别？

A4：普通断点（FPB）监视 PC——执行到某地址才停；数据观察点（DWT）监视数据访问——某个地址被读 / 写就停，哪怕执行位置无关紧要。抓 " 变量被谁改坏 "、数组越界写这类问题，DWT 才是对的工具。

### Q5：MPU 为什么会导致 " 调试正常、离线就崩 "？

A5：MPU 校验的是**内核总线上的访问**；调试器通过 AHB-AP/DAP 访问内存，走的是调试接口路径，绕开内核总线，不触发 MPU 违规。所以 MPU 权限配置错误时，调试器读写一切正常，真实程序一跑就违规 HardFault——bug 被调试器掩盖了。

## 🔴 困难

> 结合实战的深层原理和设计权衡。

### Q6：6 个 FPB 断点不够用怎么办？

A6：三板斧：① 用 DWT 比较器配置成 PC 匹配，把数据观察点临时改作指令断点，最多再补 4 个；② 合并断点——把多条路径汇到一个公共检查点，配合全局标志区分；③ 用日志流 / SystemView 非侵入观测替代部分断点（断点本身就是侵入式，数量不够往往说明问题更适合用跟踪手段）。

### Q7：Flash Patch 重映射的粒度为什么是 32 字节？

A7：因为 FPB 的 REMAP 寄存器按 32 字节对齐，patch 比较器命中时用原地址低 5 位在 32 字节块内做偏移，从而支持块内任意一条指令被替换。设计成块而非单指令，是硬件比较器位数与灵活性之间的权衡——块越小越灵活，但需要更多比较器位来编码 RAM 基址。

### Q8：离线崩溃时如何区分 " 断点改变时序 " 和 "MPU 配置错误 "？

A8：关键证据是 CFSR 与复现稳定性。CFSR 的 MemManage 位（MMFSR）明确指向 MPU 违规，再读 MMFAR 拿地址对照区域表即可坐实；而 " 断点改变时序 " 表现为：加断点消失、减断点复现，CFSR 无违规位。区分不了时，用 GPIO 翻转 + 逻辑分析仪或 SystemView 在非调试模式复现，把断点干扰排除掉。

# 📋 总结

> 3-5 句话回顾核心要点，用自己的话复述。

离线断点解决的是嵌入式调试里最头疼的 " 脱离调试器才复现 "：FPB 提供 6 个驻留芯片的指令硬件断点，是离线断点的核心载体；DWT 用 4 个数据观察点抓 " 谁改了变量 "，与 FPB 互补；内联断点（BKPT）把断点写进代码随固件走，但无调试器时必须配 DebugMonitor 才安全；FPB 的另一半是 Flash Patch 重映射，用 32 字节块的 RAM 补丁实现不重烧改代码；最后别忘了 MPU——调试器绕过内核总线不触发违规，" 调试正常、离线就崩 " 时它是最容易背锅也最容易被忽略的根因。五者合起来，就是 Cortex-M 调试体系里 " 离开调试器依然能抓住现场 " 的完整工具箱。
